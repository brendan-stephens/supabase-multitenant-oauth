How the OAuth 2.1 + PKCE flow works

The app never handles user credentials directly. It exchanges a short-lived code for a RS256-signed JWT — PKCE ensures the verifier never leaves the client.

Row Level Security

Each user only sees their own data

Tenant functions extract the sub claim from the verified JWT and use it as user_id. Postgres RLS enforces per-user row isolation.

🔐 Incoming JWT (verified by CC's public key)
iss: "…supabase.co/functions/v1/oidc"
aud: "tenant-alpha"
sub: a1b2c3d4-…
email: "alpha@demo.local"
📋 RLS Policy on tenant_notes
-- only your rows come back CREATE POLICY "own rows" ON tenant_notes FOR ALL TO authenticated USING ( user_id = auth.uid() );

Architecture

Three fully isolated Supabase projects

Only the Command Center stores user accounts. Tenants hold only application data — they trust the CC's RS256 JWT signature to establish identity.

CC

Command Center

OIDC Provider · Edge Function
  • OIDC discovery + JWKS endpoint
  • Authorization code issuance
  • PKCE (S256) verification
  • RS256 JWT signing
  • User accounts (auth.users)
  • Per-tenant access via app_metadata
  • oauth_clients + auth_codes tables
α

Tenant Alpha

Resource Server · Edge Function
  • Verifies JWT via CC's JWKS
  • Checks iss + aud claims
  • No user accounts stored
  • tenant_notes table
  • RLS: user_id = JWT sub
  • GET + POST /notes
β

Tenant Beta

Resource Server · Edge Function
  • Same pattern as Tenant Alpha
  • Separate Supabase project
  • Audience: "tenant-beta"
  • Isolated data store
  • Access controlled by CC
  • GET + POST /notes

Supabase Edge Functions

All server-side logic — OIDC provider and tenant APIs — runs as Deno Edge Functions. No separate backend infra.

jose (npm:jose@5)

RS256 JWT signing in the OIDC function. Remote JWKS verification in tenant functions via createRemoteJWKSet.

Demo App

Single HTML file — no build step. Implements full PKCE flow, one-click demo accounts, and per-tenant notes dashboard.
